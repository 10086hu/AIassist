可研报告审查智能化辅助系统
一、开发内容
本项目拟建设一套面向可行性研究报告审查场景的智能化辅助系统，整体由规则库网站、桌面端应用和核心检测智能体三部分组成，并配套建设后端服务、数据存储、文档解析、规则管理、检测结果管理等支撑能力。系统面向项目申报、项目评审、内部初审和专家辅助审查等业务环节，重点解决可研报告内容多、审查口径复杂、人工比对耗时长、审查依据分散、结果留痕不足等问题。
项目开发内容包括规则库网站建设、桌面端应用建设、核心检测能力建设等内容。
（1）规则库网站建设：规则库网站用于集中维护可研报告审查所需的评审规则，形成面向市级、区级等不同适用范围的规则知识库，为核心检测能力提供统一的规则来源和知识支撑。网站面向系统管理员、可研报告审查人员和规则维护人员，提供规则录入、规则分类、规则检索、规则更新、操作日志等功能。
（2）桌面端应用建设：桌面端应用为可研报告审查人员的主要使用入口，部署在用户的工作电脑上。用户通过桌面端完成账号登录、可研报告上传选择、检测项勾选、检测任务提交、任务进度查看、检测结果展示等操作。桌面端应用通过接口连接服务器端后端服务，检测逻辑、数据存储和规则调用统一由服务器加密处理。
（3）核心检测能力智能体：核心能力包括三个方面，一是可研报告完整性检查能力，该智能体主要负责检查可研报告文本、附件材料、表格数据和关键章节是否齐全，确保审查对象具备完整的材料基础；二是核心基础检查能力，包括建设依据审查，主要用于核查项目建设依据、政策文件、批复材料与建设内容之间是否一致；重复建设检查，主要用于识别项目内部功能点之间以及与历史项目之间是否存在重复建设或高度相似内容；建设功能的对应关系检查，主要用于检查建设内容、业务需求、系统功能、应用功能和功能点清单之间是否形成对应关系；敏感词检查，主要用于识别报告中是否存在不符合要求的词语、表达等敏感或违规内容。三是核心进阶检查能力，包括数据填报合理性检查，主要用于核查用户量、业务量、并发量、数据量、存储量等填报指标是否合理；资源申请的合理性检查，主要用于判断云资源、硬件资源和软件资源申请是否与项目规模、功能需求和性能要求匹配；安全内容的合理性检查，主要用于检查安全需求、安全建设内容和项目实际建设范围是否匹配；价格合理性检查，主要用于结合软件造价、产品价格和市场参考价判断项目预算是否合理；软硬件产品价格参考，主要用于对软硬件产品型号、品牌、数量和单价进行参考比对，为价格审查提供依据。
二、交付目标和考核指标
本项目交付目标是形成一套可部署、可使用、可维护、可扩展的可研报告智能审查辅助系统，搭建规则库网站与桌面端应用，提供完整性检查、建设依据检查等核心检测能力，为可研报告审查提供规则维护、报告解析、检测任务创建、结果展示、结果导出等能力。项目交付后，应能够支撑审查人员对可研报告开展自动化、结构化、智能化的辅助审查，提升审查效率和审查一致性。
（1）主要交付物
项目交付物包括软件系统、用户使用文档两类。
1.软件系统交付物
交付规则库网站一套，包含规则录入、规则分类、规则检索、规则更新、操作日志等功能。
交付桌面端应用一套，包含登录、报告选择、检测项勾选、任务提交、结果展示等功能。
交付后端智能体服务一套，核心需包含一是可研报告完整性检查能力；二是核心基础检查能力，包括建设依据审查，重复建设检查，建设功能的对应关系检查，敏感词检查。在此基础上，结合项目实施条件、数据基础、规则完善程度及实际应用需求，可进一步开展核心进阶检查能力的建设与优化，包括数据填报合理性检查、资源申请合理性检查等内容。

（2）功能考核指标
1.规则库网站功能指标
规则库网站支持规则新增、编辑、删除、查询。
规则库网站支持按规则类型、适用范围、规则状态、标签等条件进行检索。
规则库网站记录规则变更日志，能够查询规则修改人、修改时间和修改内容。
规则库网站维护的有效规则应能够被后端检测服务调用。
2.桌面端应用功能指标
桌面端应支持用户登录、退出和主工作台展示。
桌面端应支持选择可研报告及相关附件，并对文件格式进行基础校验。
桌面端应完整展示完整性检查能力、核心基础能力以及构建的核心进阶能力，支持单项选择、多项选择、全选和清空。
桌面端应能够向后端提交检测任务，并展示任务创建、执行、完成和异常状态。
桌面端应能够展示检测结果明细，包括检测项、问题描述、风险等级、判断依据、原因说明和整改建议。
3.检测功能指标
核心指标：
完整性检查应能识别可研报告文本、附件材料、表格数据和关键章节是否齐全
建设依据审查应能够识别依据缺失、依据不匹配、依据描述不完整等问题。
重复建设检查应能够对本报告内部功能点、建设内容进行相似度比对，也应能够对本报告与关联报告之间的建设内容进行跨报告比对，并输出疑似重复项、重复来源、相似原因和复核建议。
建设功能对应关系检查应能够识别建设内容、需求分析、功能设计之间的一致性问题。
敏感词检查应能够识别报告中是否存在不符合要求的词语、表达等敏感内容。
结合项目实施条件、数据基础、规则完善程度及实际应用需求，系统可尝试构建并支持以下核心进阶检查能力：  
数据填报合理性检查应能够识别关键数据缺失、数量级异常、前后口径不一致等问题。
资源申请合理性检查应能够识别资源配置与业务规模、功能需求、性能需求不匹配等问题。
（3）性能与稳定性考核指标
响应性能：规则库网站与桌面端应用应在正常网络环境下保持较好的响应速度，无明显卡顿，对于网络异常情况及时向用户反馈。
检测任务性能：系统应支持单个项目同时选择多项检测并创建检测任务，实时提供检查进度可视化反馈。
稳定性：系统应保持7×24小时稳定运行，支持多个任务同时处理，不能因单个文件解析失败或单项检测异常导致整体服务不可用。
三、技术路线
（1）技术路线一：规则库网站
规则库网站按“前端规则维护 + 后端接口服务 + 数据库存储 + 检测服务调用”的方式实现。前端采用 Vue3 + Element Plus 构建规则库管理界面，提供规则新增、编辑、删除、查询、标签管理、审核入库、撤回审核和操作日志查看等功能；后端采用 Python 接口服务对规则数据进行统一管理，规则数据存储在 MySQL 数据库中。每条规则主要包含规则名称、规则类别、规则详情、市级判断标准、区级判断标准、规则标签、审核状态、更新时间等字段，支持按规则状态、规则类别、标签和关键词进行快速检索。规则创建后默认进入待审核状态，经审核通过后作为有效规则入库，并可被后续桌面端检测服务通过接口调用。网站同时记录规则新增、修改、删除、审核和撤回等操作日志，保证规则来源清晰、状态可追溯、变更有留痕，为九项检测能力提供统一、可维护、可扩展的规则知识支撑。
（2）技术路线二：桌面端应用
本路线采用 Windows 桌面客户端加服务器后端接口的架构，桌面端技术栈为 .NET 9 + WPF + C#。其中 .NET 9 作为应用运行框架，WPF 用于构建 Windows 图形界面，界面布局通过 XAML 实现，按钮点击、页面切换、文件选择、检测项勾选等交互逻辑通过 C# 实现。用户后续通过 HTTP / HTTPS 内网接口调用服务器端 FastAPI 服务，将报告文件、检测项和项目信息提交到后端，由服务器完成文档解析、规则审查、数据库存储和结果生成，再由 WPF 客户端查询任务状态并展示审查结果。
（3）技术路线三：核心能力建设
可研报告完整性检查能力
完整性检查按“文件可读性检查＋报告主体检查＋主要表格检查＋依赖附件检查”实现。桌面端上传可研报告及配套附件后，后端解析可读取的正文和表格，检查建设方案与投资预算主体是否明显残缺，已识别的建设功能、设备采购、服务内容及预算等主要表格是否只有表头或占位内容，并核对正文明确依赖的主要附表和必要附件是否已提供。对于已在同类正文中作出实质说明的内容，接受等效表达；对于图片、扫描内容或附件无法可靠读取的情况，提示人工核实。检查结果展示缺失或待核实事项、判断依据、原文位置和补充建议，并支持导出。完整性检查的“通过”仅表示未发现明显材料残缺，不代表报告内容的充分性、数据正确性或其他专项审查已经通过。
核心基础检查能力
1.建设依据审查模块为政务数字化项目可研报告提供自动化政策合规性审查能力，覆盖建设背景及依据、必要性分析等核心章节的语义解析与条款核验。系统基于规则引擎驱动与NLP语义辅助的混合架构，通过大模型语义匹配自动识别政策引用准确性、建设必要性充分性及附件原文真实性。支持PDF与Word格式政策文件的版式解析与核心条款结构化提取，实现可研摘要与政策原文的双层一致性校验（关键词匹配+连续短句硬匹配），确保每条审查结论均可追溯至具体规则配置。
2. 重复建设检查采用“文档解析、功能点提取、相似性分析、智能复核与结果存储相结合”的技术路线，实现了多格式文件接收与解析、功能点自动提取、重复及相似功能识别、检测结果存储与展示等功能。系统对同一份材料中的功能点进行综合比对，筛选疑似重复项，并通过智能复核区分重复、高度相似和无关内容，形成包含关联功能点、相似度、风险等级、判断原因及整改建议的结构化结果，为桌面端展示和人工复核提供支持。
3.建设功能的对应关系检查采用“章节解析 + 要素抽取 + 对应关系构建 + 规则校验 + 大模型复核”的技术路线。桌面端上传可研报告后，后端解析正文及表格，识别建设依据、项目摘要、建设目标、建设内容、建设周期、需求分析、功能设计及功能点清单等关键章节，抽取相关要素，并结合规则库中的市级、区级判断标准开展一致性校验。实现了核查项目主要建设内容与建设依据是否逐条对应，确保建设内容与政策依据及其摘要形成对应关系；检查全文建设依据的一致性，核对项目摘要中列举的建设依据与附表中的政策依据是否一致；校验全文建设目标、建设内容及建设周期的描述是否前后一致；审查建设依据与建设内容的相关性，判断建设依据的摘要描述是否与本项目建设内容相关。同时，构建“建设内容—业务需求—系统功能—应用功能—功能点清单”对应关系，识别内容缺失、功能不匹配及前后描述不一致等问题。对于语义复杂或存在歧义的内容，调用大模型辅助复核，最终结果展示出问题位置、命中规则、判断依据、原因说明和修改建议。




4.敏感词检查按“敏感词抽取 + 规则库匹配 + 语义场景识别 + 风险分级输出”实现。后端解析可研报告正文、附件材料、预算表、技术路线、系统架构、设备配置及相关说明等内容，抽取其中可能存在的非信创敏感词、厂商名字等需重点关注的表达，形成敏感内容词库。规则库中维护敏感词条、同义表达和需人工确认项，系统先通过关键词匹配、同义词归一和模式识别发现疑似敏感内容，再结合上下文判断其属于拟采用表述、现状描述、引用说明、政策转述还是其他语义场景。对于容易产生歧义或误判的表述，结合语义分析能力和大模型进行分类和风险复核。最终输出疑似敏感词或敏感表达、所在章节、上下文片段、判断依据、风险等级和修改建议，对明显不符合要求的表述标记为较高风险，对引用说明、背景描述或需结合上下文进一步判断的内容标记为低风险或需人工确认。



5.数据填报合理性采用“文档结构解析 + 金额与指标提取 + 数据口径归一 + 分层规则校验 + 原文证据回溯”的技术路线。桌面端上传可研报告后，后端解析正文及表格，提取项目总投资、预算明细、成效考核目标和数据治理服务等可识别内容，并结合项目适用范围开展检查。在预算方面，通过金额单位归一和表内、表间可比数据核对，实现项目预算一致性校验，检查各分项的投资估算明细表内部计算无错误、表间的计算总和无错误，所有分项明细表总计与项目投资总预算一致。在成效考核目标方面，通过定位指标章节或表格、识别指标类别并统计有效指标数量，实现项目成效考核目标数量设置合规性审查，检查通用指标中至少设定3个效益指标，业务指标中至少设定4个产出指标或效益指标；涉及智能化应用的需明确不少于2个成效指标。
6.资源申请合理性采用“多格式材料解析 + 资源要素抽取 + 服务名称归一 + 数量及配置关系校验 + 原文证据定位”的技术路线。桌面端上传可研报告或资源清单后，后端解析正文及表格，提取可识别的资源名称、数量、计量单位、清单来源和配置说明。对于安全服务需求表、PaaS服务清单、密码服务资源内容清单，通过同类服务名称归一、来源区分和同口径数量比对，实现关联内容一致性校验，检查安全服务需求表、PaaS服务清单、密码服务资源内容清单中的关联内容数据应一致。对于服务器、操作系统、数据库服务器和数据库等资源，通过资源类型识别、数量提取及配置关系核对，实现三大件数量一致性校验，检查每新申请一台服务器需配一套操作系统；每申请一台数据库服务器需配一个数据”，并结合材料中明确的统一部署、共享使用或复用说明形成判断。检查结果展示参与比对的数量、问题位置、原文依据、原因说明和修改建议；来源、单位、建设阶段或部署覆盖关系不明确时，提示资料不足或需要人工核实，不直接认定资源缺配。
  
核心进阶检查能力
1.安全内容合理性检查模块：采用“文档解析、要素提取、规则校验与大模型辅助审查相结合”的技术路线，针对第4.7节“安全需求分析是否满足要求”的审查要求，已实现安全需求分析章节识别，以及安全风险分析、安全等级定位、数据分类分级、安全防护措施和密码应用措施五项核心内容的完整性检查。系统能够识别章节缺失、关键内容缺项及安全等级不一致等问题，输出审查结论、风险等级、判断依据和修改建议，为人工复核提供支持。2. 价格合理性检查：采用“功能点解析、计价规则匹配与费用核验相结合”的技术路线，重点评估软件开发费用。目前已解析《二类费用计价标准》，实现了相关费用的标准限额测算、申报金额比对、重复申报及合计占比校验，并支持软件开发工作量、人月单价和金额计算一致性检查，输出异常提示及修改建议。3. 软硬件产品价格参考：采用“价格数据管理、产品清单解析、标准化匹配与价差分析相结合”的技术路线，已实现软件开发人月单价及功能点工作量校验，包括2.5万元基础单价、数字化新技术应用可调整至3万元，以及单个功能点1—5人月的工作量范围。针对软硬件产品计量计价要求，已实现价格参考数据导入、产品名称及品牌型号规格匹配、申报价格与参考价格比对和异常提示.    4. 数据治理服务内容设计合规性审查通过报告正文与数据治理服务附表解析、项目适用性识别、服务事项标准化匹配及指引规则校验，实现了数据治理服务内容设计合规性审查功能。涉及数据治理服务的项目，数据服务事项内容参照《市级数字化项目数据治理服务配置指引（试行）》开展编制。系统对可识别的服务事项、类别、测算单位、适用阶段和负面清单内容进行核验，结合相关正文提示服务边界或交付依据需核实的事项，并保留问题依据及原文位置；对材料不足或政策适用条件不明确的情况提示人工复核。
四、计划进度
第一阶段：规则库与桌面应用：完成项目基础能力建设，形成规则库雏形和桌面端应用原型，具备规则资料管理、审查任务入口、报告选择、检测项配置和任务发起等基础能力，为后续检测能力接入提供基础支撑。对应产出包括规则库网站初版、桌面端应用原型、基础功能页面、检测项配置入口和系统基础说明材料。
第二阶段：核心检测能力框架搭建与完整性检查能力建设。完成统一检测流程和报告解析能力建设，形成可扩展、可复用的检测框架，并优先实现可研报告完整性检查。重点验证文件可读性、报告主体明显残缺、主要表格为空及明确依赖的附件缺失等场景，明确完整性结论与专项审查结论的边界。对应产出包括检测框架、完整性检查模块、规则清单、报告结构识别结果、检查结果模板和测试样例。
第三阶段：核心基础检测能力建设：完成基础类检测能力建设，覆盖建设依据审查、重复建设检查、建设功能的对应关系检查和敏感词检查，能够对报告中的政策依据、功能重复、内容对应关系和信创符合性进行初步审查，形成基础检测结果。对应产出包括基础检测能力模块、基础检测规则清单、检测结果分级标准、问题原因与修改建议模板、基础检测报告和阶段测试材料。
五、后续工作
后续将在此基础上，重点提升可研报告正文、表格及附件的结构化解析和跨材料关联核验能力，完善资源申请合理性的场景化判断，强化预算数据、成效指标和数据治理服务内容的检查。完整性检查将从核心材料缺口预检，逐步扩展至章节、标记内容、主要表格及必要附件的分类核验，并探索扫描材料识别和语义充分性辅助复核。
在新增进阶审查能力方面，拟开展安全内容合理性检查，将安全需求、建设措施与项目建设范围关联起来，结合规则校验和模型辅助判断，识别内容缺漏或对应关系不清的情况。价格合理性检查将围绕软件开发内容、工作量和费用依据建立核算与差异提示能力，逐步提高费用审查的可解释性。软硬件产品价格参考将建设参考价格数据的维护、匹配和比对能力，为产品采购价格审查提供来源可核验的参考依据。同时，完善规则与政策版本管理、原文证据定位、人工复核及案例测试机制，对依据充分的事项形成可追溯结论，对口径、适用条件或参考依据不明的事项提示人工确认。
