# 融合版本使用与回归

本版本以当前项目为基线，接入 `AIassist-local-20261102.zip` 的真实认证、管理员 API、历史记录上报和分发、记录打包、服务器收件箱、原报告另存与部署支持。

保留当前建设依据识别、敏感词字符及表格定位、AI 完整中文意见和逐项状态、问题记忆版本链、完整 HTML 审查报告导出、资源缺项提示、蓝白业务窗口、原登录视觉和深色侧栏。未引入 ZIP 中已被取消的建设功能随机选择展示逻辑。

## 本地启动和首次登录

1. 运行项目根目录 `run_backend.bat`，保持后端运行。
2. 运行 `run_desktop.bat`。
3. 首次使用新版，需要在原登录页注册真实本地账号，再登录。以前仅用于显示操作人的账号不会自动生成真实密码。
4. 账号长度为 3～32 位，以英文字母或数字开头，可包含 `_ . -`；注册密码 12～128 位，不能全部为空白。
5. 本地普通账号即可新建项目、执行检查、查看原文、选择记忆基准、导出审查报告。登录过期后需要重新登录。

免登录浏览保留页面浏览能力，但不会加载业务记录或执行检查。

当前注册页的单位输入保留原视觉；后端账号协议没有单位字段，该输入不作为已经保存的单位档案。用户名、密码和显示名称遵循后端真实协议。

### 环境和原数据兼容

- 原 `backend/.venv` 如果引用另一台电脑的 Python，启动脚本会改用本机创建的 `backend/.venv-local`，不删除原环境。
- 显式 `DATABASE_URL` 优先，不在日志打印可能包含密码的连接串。
- 未显式配置时，若旧 `%TEMP%\AIassist\app.db` 存在，继续使用旧库，避免切到另一份空库；否则默认项目 `.runtime\app.db`。
- 想明确改用项目目录，可在启动前设置 `AIASSIST_DATA_DIR`。这只是选择位置，不会自动合并两份数据库。
- 更新前建议备份实际使用的 SQLite 数据库；本次回归仅使用隔离数据库，没有迁移或改写用户现有记录。
- 后端新增账号和历史传输表，保留原问题记忆两表、项目、结果、附件等。启动迁移保持幂等，并恢复上次进程中断的运行批次状态。

## 本地与服务器的账号范围

本地账号和服务器账号分别注册、分别登录，令牌不能混用。

| 后端模式 | 普通账号 | 管理员 |
| --- | --- | --- |
| local | 可使用本地审查工作区，导入分发记录 | 同时具备账号管理权限 |
| server | 可上报自己的历史、领取分发给自己的记录 | 可管理服务器审查工作区、查询上传、分发与撤回、管理账号 |

本地业务工作区仍是同一数据库中的共享工作区，没有新增项目所有权隔离；服务器的个人上传与收件箱按账号隔离。不要把真实登录理解为新增了完整多租户项目管理。

普通账号不会自动成为管理员。先注册目标账号，在目标后端的相同数据库环境下，从 `backend` 目录执行：

```powershell
.\.venv-local\Scripts\python.exe -m app.cli.manage_admin 用户名 --role admin
```

服务器容器内可使用对应 Python 执行相同模块。角色变更会撤销旧会话，需重新登录。管理员目录与账号管理接口位于 `/api/admin`；最后一个启用的管理员受到保护。

## 服务器收件箱与原报告另存

1. 在“审查记录”页点击“服务器收件箱”。
2. 输入实际服务器 API 地址，登录被指定接收记录的服务器账号。
3. 在“保存到本机”区域登录本地账号；已登录相应本地后端时复用当前会话。
4. 刷新并选择待接收、已接收或全部记录，支持分页。
5. 选择记录后“保存到本地”。客户端先下载校验、写入本地数据库，再向服务器确认接收。
6. “查看本地记录”进入本地工作区，查看已保存的结果、问题记忆和原文。
7. 在审查详情点击“另存原始报告”。原报告文件与完整 HTML 审查报告是两种不同导出，两者都保留。

已保存但确认失败时，可重试同一条记录，不会重复创建项目。服务器的已接收状态不保证当前电脑有副本，换电脑后仍可重新领取。撤回阻止后续领取，不会删除用户已经保存到本地的副本。

新收件箱窗口和业务提示沿用当前蓝白组件，文件打开与另存仍使用系统窗口。

## 历史上报和管理员分发

包内新增上报和分发是后端 API 能力，本次保留；ZIP 原本也未提供完整的桌面管理员分发控制台。

可通过后端 `/docs` 使用接口：

1. 向本地 `/api/auth/login` 登录，在文档的 Authorize 填入本地令牌。
2. `GET /api/history/exports/{project_id}` 导出记录包，可指定检测批次。
3. 向服务器登录并取得服务器令牌，将包和新的 `client_record_id` 提交到 `POST /api/history/uploads`。
4. 管理员通过 `/api/admin/history/uploads` 查询上传记录。
5. 管理员向 `POST /api/admin/history/deliveries` 提交目标账号、服务器项目和可选批次。
6. 接收者通过桌面收件箱保存。管理员可查询分发记录或调用撤回接口。

同一上传编号只能对应同一内容；修改后的新记录应使用新编号。传输过程保留结果快照，不为接收动作重新运行审查。

## 问题记忆的传输兼容

- 无记忆的旧记录保留 v1 传输格式及原校验规则。
- 包含问题记忆的记录使用 v2，携带版本基准、问题快照和必要历史节点；服务器与本地都应使用融合后版本。
- `/api/history/capabilities` 可查询协议版本。客户端遇到不支持 v2 的目标，会提示升级，不会静默丢掉记忆再标记成功。
- 批次传输会包含必要的历史祖先，因此收到的项目可能含有多次历史检查。
- 已删除的历史原记录无法凭空恢复，接收结果会明确显示历史不完整；旧 v1 仅有记忆文字的快照也会明确标注。
- 项目、批次、结果、附件及问题引用一致映射到接收端，避免指向原服务器或覆盖其他本地记录。
- 检测范围、规则签名和原结论仍按历史版本保存，不能把历史通过当作新规则下已经通过。

沿用 ZIP 的传输限制：附件合计最多 32 MiB，记录包最多 48 MiB，请求最多 50 MiB；最多 200 批次、2000 结果、500 附件。超过限制会明确拒绝，不截断内容。大报告或多版本祖先可能超过该预算；即使单批次也超过时，当前协议不支持分块传输。
