# 可研报告审查共性技术与智能体建设方案

## 一、结论摘要

可以开发相关智能体，但不宜把智能体简单理解为“接入大模型的聊天检索框”。更可行的方向是建设一个**受规则约束、以证据为中心、可调用业务工具的审查与编制智能体平台**：

1. 当前系统已经具备智能体所需的基础积木：多格式文档解析、结构化字段抽取、规则匹配、相似度比对、大模型复核、结果规范化、原文定位、规则来源记录和审查结果留痕。
2. 九项检测中的重复建设、资源申请合理性、建设依据、功能对应关系、数据填报、安全、价格和信创检查，本质上都可以归并到同一套“材料理解 -> 知识/规则取证 -> 工具执行 -> 结论生成 -> 人工复核”的通用流程。
3. 智能体应先服务于**检索、审查、解释和修改建议**，再逐步扩展到**辅助生成审查意见、整改稿、结构化清单和报告章节**。生成结果必须带引用、保留原文、记录规则版本，并经过校验和人工确认。
4. 建议采用“确定性工具优先，大模型负责语义理解和编排”的混合架构。涉及金额、数量、阈值、合规结论的内容不能仅由模型自由生成。

## 二、现有技术盘点

### 2.1 已有能力

| 能力 | 当前实现或依据 | 可复用价值 |
|---|---|---|
| 文档解析 | `duplicate/document_parser.py`、`excel_parser.py`，支持 Word/Excel/CSV 等材料 | 统一材料接入、章节和表格抽取 |
| 功能点抽取 | 重复建设模块的大模型抽取链路 | 可扩展为业务对象、指标、资源、产品和依据抽取 |
| 文本标准化与相似度 | `duplicate/embeddings.py`、关键词/向量混合筛选 | 候选召回、实体归一化、历史项目比对 |
| 规则执行 | `services/check_service.py`、各检测模块规则与 Excel 规则库 | 可解释、可审计、稳定执行 |
| 大模型复核 | `core/llm_client.py`、重复判断和安全审查 | 处理语义判断、原因说明、建议生成 |
| 结果统一化 | `result_refiner.py`、API 层的结果规范化 | 统一前端展示和后续生成输入 |
| 证据和来源追溯 | `CheckResult`、`SourceArtifact`、来源定位字段 | 支持引用、复核、重新打开原文 |
| 任务与接口 | FastAPI `/api/evaluate/*`、任务状态和结果接口 | 为智能体提供工具调用入口 |
| 知识数据模型 | `KnowledgeDoc`、`DocChunk`、`PriceBenchmark`、规则和审计表 | 可演进为统一知识库和检索索引 |

### 2.2 当前短板

- 各模块接口和结果字段仍有差异，尚未形成统一的检测工具协议。
- `backend/app/retrieval` 目前基本为空，知识库的分块、索引、混合检索、重排和引用服务需要补齐。
- 规则、知识文档、历史项目、价格数据和报告证据尚未形成统一的对象标识、版本和权限模型。
- 大模型调用主要嵌在具体模块中，缺少统一的模型网关、提示词版本、重试、缓存、成本和质量监控。
- 生成能力尚未建立“模板 + 结构化数据 + 引用 + 校验”的闭环，暂不应直接生成可作为正式审查结论的内容。

## 三、应沉淀的共性技术

建议把共性技术建设为平台层，检测模块成为平台上的领域插件。核心不是增加更多独立智能体，而是统一以下六类能力。

### 3.1 统一材料理解层

建立 `Document -> Section -> Table -> Cell/Paragraph -> Evidence` 的统一中间表示（IR），保留文件、页码/章节、表格行列、文本偏移、版本和哈希。

通用处理流程：文件识别与病毒检查、格式解析、版面/章节切分、表格结构恢复、OCR（必要时）、文本清洗、字段抽取、实体和术语归一化。所有抽取字段都应保存 `source_span` 和置信度，不能只保存模型最终文字。

### 3.2 统一知识检索与取证层

知识对象至少包括规则、政策法规、标准规范、审查指南、术语、历史项目、价格基准和已确认的审查案例。采用关键词 + 向量的混合召回，结合元数据过滤和重排；返回内容必须包含文档版本、来源、适用范围、生效时间和引用片段。

检索服务建议提供统一接口：

```text
search(query, scope, filters, top_k) -> chunks[]
get_evidence(evidence_id) -> 原文片段与来源定位
get_rule(rule_id, version) -> 规则、条件、阈值、例外
```

### 3.3 规则与工具执行层

把确定性能力包装为可调用工具，并规定输入输出 JSON Schema：

- `parse_document`：解析材料并返回统一 IR。
- `extract_objects`：抽取功能点、指标、资源、产品、依据等对象。
- `run_rule_check`：执行规则、公式、阈值和字段完整性校验。
- `compare_items`：执行内部、跨报告、历史项目相似度比对。
- `lookup_price`：匹配产品和价格基准并计算偏差。
- `locate_source`：根据证据 ID 定位原文。
- `render_report`：依据模板生成草稿并保留引用。

工具应具有幂等性、超时、重试、权限和审计信息；工具结果应区分“通过、发现问题、需人工确认、工具失败”，不能把工具失败误报为业务结论。

### 3.4 模型网关与提示词工程

统一封装模型供应商、模型版本、超时、限流、重试、JSON 输出校验、脱敏、缓存和费用统计。提示词作为版本化资源管理，输入只传必要证据，输出使用固定 Schema。

模型职责建议限定为：语义抽取、候选归类、冲突解释、依据摘要、修改建议和草稿生成；不直接决定金额计算、阈值判定、规则生效状态和最终合规结论。

### 3.5 结果、证据和反馈闭环

统一审查结果结构：

```json
{
  "finding_id": "...",
  "module": "duplicate",
  "label": "部分重复",
  "severity": "需人工确认",
  "reason": "...",
  "evidence": [{"evidence_id": "...", "quote": "...", "location": {}}],
  "rule_refs": [{"rule_id": "...", "version": "..."}],
  "suggestion": "...",
  "confidence": 0.82,
  "review_status": "待复核"
}
```

审查人员的接受、驳回、修改和补充依据都应作为反馈样本，反哺规则优化、术语词典、召回评估和提示词评估，而不是直接无审核地用于模型训练。

### 3.6 安全、权限和可观测性

报告原文、政策材料和审查意见可能包含敏感信息。平台应支持租户/部门/项目级权限、字段脱敏、内网模型或可控模型路由、操作审计、数据保留策略、模型输入输出留痕和人工复核状态。关键指标包括检索命中率、引用覆盖率、规则执行成功率、模型 JSON 合法率、人工采纳率、幻觉率、平均时延和单任务成本。

## 四、智能体形态与边界

### 4.1 推荐的智能体分层

建议采用一个面向用户的“审查与编制助手”作为入口，内部由编排器调用若干专业能力，而不是让多个智能体自由对话：

1. **材料分析智能体**：识别文档类型、章节、表格和项目对象，触发解析与抽取工具。
2. **依据检索智能体**：根据问题和项目上下文检索规则、政策和历史案例，返回带引用证据。
3. **专项审查智能体**：按模块调用重复建设、功能对应、数据、资源、安全、价格和信创工具。
4. **审查解释智能体**：将结构化结果转换为可读原因、风险说明和整改建议，禁止脱离证据扩写。
5. **辅助生成智能体**：在用户指定范围内生成审查意见草稿、整改清单、项目章节或结构化表格，并逐段附引用和校验状态。
6. **复核编排智能体**：识别证据冲突、低置信度和规则缺失，转交人工，不自行“拍板”。

### 4.2 典型工作流

```text
用户问题/上传材料
  -> 材料解析与对象抽取
  -> 检索规则、依据、历史案例
  -> 调用确定性检查工具
  -> 对候选问题进行模型复核
  -> 汇总证据、规则版本和风险等级
  -> 输出可追溯结果
  -> 用户确认后生成审查意见/整改稿
```

智能体的每一步都应产出可检查的中间状态（计划、工具调用、证据、结论），前端可先展示“待确认草稿”，再允许导出或写回正式材料。

### 4.3 生成能力的适用范围

适合优先生成：审查结果摘要、问题清单、整改建议、依据摘要、章节大纲、字段补全草稿、询问清单和多版本表述。

需要人工确认后生成：正式审查意见、预算调整建议、项目建设方案章节、对外报送文本。

不应自动生成或自动生效：最终合规结论、政策适用判断、金额和数量的最终值、规则库生效版本、涉及采购倾向或供应商推荐的结论。

## 五、分阶段建设路线

### 阶段 0：共性底座（4-6 周）

- 定义统一 IR、Evidence、Finding、Rule、Task 和 AgentRun 数据结构。
- 把现有模块结果适配到统一 Finding Schema。
- 建立统一模型网关、JSON 校验、重试、缓存、提示词版本和审计。
- 补齐知识文档分块、混合检索、重排、引用和权限过滤。
- 将现有 API 封装为工具协议，先不改变九项检测业务逻辑。

验收重点：同一份材料可被多个模块复用；每条问题均可回到原文和规则版本；模型失败不影响确定性检查结果。

### 阶段 1：检索与审查助手（6-8 周）

- 支持“针对本报告查询依据/规则/历史案例”。
- 支持一键执行单项或组合审查，显示任务计划、证据和中间结果。
- 优先打通重复建设、建设依据、功能对应、数据填报和资源合理性五类能力。
- 建立 30-50 份脱敏样本的离线评测集和人工复核流程。

验收重点：引用准确、结果可复核、检索不越权、重复执行可复现。

### 阶段 2：审查意见与整改草稿生成（6-10 周）

- 以结构化 Finding 和已确认证据为唯一输入生成草稿。
- 提供“保守改写、补充说明、压缩摘要、按模板成文”等生成模式。
- 逐段显示引用、规则依据、未确认项和生成置信提示。
- 由审查人员确认后导出 Word/Excel，不直接覆盖原始报告。

验收重点：引用覆盖率、事实一致性、数字一致性、人工采纳率和可编辑性。

### 阶段 3：辅助编制与闭环优化（持续）

- 根据项目基本信息和已确认规则生成章节大纲、指标表、资源说明和整改后版本。
- 建立规则/术语/案例的反馈闭环和版本评估。
- 结合本地模型、私有化部署或多模型路由，降低敏感材料外发风险和调用成本。

## 六、优先级与投入建议

建议优先投入共性底座，而不是先开发多个“会聊天”的智能体。最小可行版本可由现有 FastAPI 后端扩展：

1. 统一 `retrieval` 服务和证据对象。
2. 统一 `agent_runs`、工具调用和生成草稿表。
3. 将现有 `evaluate` 接口注册为工具。
4. 增加一个审查编排接口，例如 `POST /api/agent/runs`、`GET /api/agent/runs/{id}` 和 `POST /api/agent/drafts/{id}/approve`。
5. 在 WPF 中增加“依据问答/审查助手/生成草稿”三个入口，先展示草稿和证据，不自动提交正式结果。

在数据规模较小的早期阶段可以继续使用 PostgreSQL/SQL Server + 对象存储 + 向量索引的组合；若暂时不引入独立向量数据库，也可以先以 `DocChunk` 和可替换的索引适配器实现，避免把检索引擎绑定在业务模块中。

## 七、主要风险与控制措施

| 风险 | 控制措施 |
|---|---|
| 模型编造依据或数字 | 强制引用；数字从结构化字段和工具结果读取；无证据不得生成肯定结论 |
| 规则版本变化导致结果不可复现 | 规则、知识文档、提示词和模型均记录版本 |
| 长文档超时和成本过高 | 分章解析、缓存、候选召回后再调用模型、异步任务队列 |
| 不同模块口径不一致 | 统一 Schema、规则 ID、风险等级和术语词典 |
| 误把模型意见当作最终结论 | 输出“模型建议/需人工确认”状态，保留人工复核和回退入口 |
| 敏感报告外发 | 内网部署、脱敏、模型路由和访问审计 |

## 八、建议形成的项目成果

最终应形成的不只是一个检索界面，而是一套可复用的**审查智能体共性技术平台**：统一材料理解、知识检索、规则执行、模型编排、证据追溯、结果生成、人工复核和质量评估。九项检测是首批专业工具；后续可将平台复用于项目立项材料审查、预算审核、建设方案编制、答疑材料生成和历史项目知识问答。

总体判断：技术上可行，且现有项目已经具备较好的起点。建议按“共性底座 -> 检索审查 -> 有证据生成 -> 辅助编制”的顺序推进，把智能体定位为审查人员的可控协作工具，而不是替代审查责任主体的自动决策系统。
